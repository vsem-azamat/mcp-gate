# Downstream servers

[Docs](../README.md) / [Architecture](README.md) / **Downstream servers**

How mcp-gate connects to the MCP servers behind it. The behaviour is specified in [`openspec/specs/downstream-lifecycle/spec.md`](../../openspec/specs/downstream-lifecycle/spec.md). `mcp-gate serve` runs one supervisor per enabled server (see [Serving](serving.md)); `mcp-gate check -connect` runs them to try a config.

## Supervisor

`downstream.New(opts)` builds a supervisor and `Start` runs its loop in one goroutine: connect, watch the session, tear it down, wait in backoff, connect again. Callers use `Call(ctx, fn)`, which hands `fn` the current `*mcp.ClientSession` and counts the call as in flight; `Status` and `Wait` report the state. `Stop` ends the loop and the child and cancels the calls in flight, since closing a session waits for them.

`Options.Notifications` holds the handlers for the server's progress, log messages and list changes, which the SDK calls one at a time on the session's reader, and `OnSession` is called with each new session once it is ready. On `2026-07-28` sessions the SDK opens `subscriptions/listen` for the list changes it has handlers for, but does not wait for the answer, so a server that rejects it would never report a change. A receiving middleware records the session whose server sent `notifications/subscriptions/acknowledged`; until then, every successful probe calls the list-changed handlers, and the mirror lists again.

Connecting builds a fresh transport each time. Without a pin, the handshake runs under a 5 s sub-deadline: the SDK client sends `server/discover` first and falls back to `initialize` only on an error reply, so a server that ignores discover would otherwise block until the connect timeout (60 s) and then fail. When the sub-deadline expires, the attempt is torn down and repeated offering `2025-11-25`. Silence alone cannot tell a server that ignores discover from one that is slow to start (a cold `npx` cache), so the pin is kept for later connects, and reported through `OnPinLearned`, only when the pinned handshake completes within the sub-deadline; otherwise the next connect tries discover again.

The watch loop wakes on the child's exit, on the session ending (`ClientSession.Wait`), on `Stop` and on the probe ticker. A probe is skipped while a call is in flight and ignored when a call started during it, because single-threaded servers cannot answer a ping while they work. Only failures that are not JSON-RPC error replies count; the SDK reports transient HTTP statuses such as 503 as code -32005, which counts as a failure. The third failure in a row closes the session, but only with no call in flight.

## Stdio

The gate does not use the SDK's `CommandTransport`, which signals only the leader and ends the connection on a frame over 16 MiB. `procutil.Start` creates the pipes itself and starts the command with `Setpgid`, so the child leads a process group, and hands the child its ends as files: `cmd.Wait` then never waits for copying goroutines, and the group can be killed as a whole. `Stop` closes stdin, sends SIGTERM to the group, polls until the leader is reaped and `kill(-pgid, 0)` reports the group empty, then repeats with SIGKILL. On Linux a zombie member keeps the group from being empty until it is reaped; on darwin `kill(-pgid, 0)` skips zombies and fails with `EPERM` when only they are left, so `Stop` can return while a grandchild left to `launchd` is still a zombie. Once the leader is reaped and the group is empty, its PID may be reused, so no further signal is sent to it. Members reparented to the gate are reaped with `wait4(-pgid)` once the leader is gone. Once the group is gone, `Stop` waits for the stderr reader to reach EOF, so the last lines the child wrote are kept, and closes the read end after one second when a process outside the group (one that left it with `setsid` or `setpgid`, or one the gate cannot signal) still holds the pipe; when the group survived SIGKILL it closes it at once. Stdout is closed without draining, since the connection on it is done.

`lineConn` implements `mcp.Connection` on the pipes. It reads frames with a `bufio.Reader`; a frame over `maxMessageBytes` (counted without its line ending, `\n` or `\r\n`) is consumed to its newline, keeping only its first and last kilobyte. The id is taken from either end, since most servers write it first and the TypeScript SDK last. When the head shows a response (a top-level `result` or `error` before any `method`, so that a request from the server with a colliding id is never taken for one) and the id names a request the gate sent that is still pending, a JSON-RPC error response is delivered in place of the frame. An id is dropped from the pending set when its response arrives or its cancellation is sent. A dropped response whose id cannot be found leaves its call waiting until `callTimeout`; with `callTimeout: 0s` that call, and the probes it suspends, wait for good. Lines that do not decode are skipped.

`procutil.EnableSubreaper` sets `PR_SET_CHILD_SUBREAPER` and reaps, on SIGCHLD and every second, zombie children that `Start` did not create (orphans that left the group with `setsid`). It lists the gate's children from `/proc/self/task/*/children`, the children of each of its threads, since an orphan is reparented to one of them, or by scanning `/proc` on a kernel built without those files (`CONFIG_PROC_CHILDREN`). Only the check of each listed child (a zombie whose parent is the gate) and its reaping hold the lock under which `Start` registers its children, so a child being started is never taken for an orphan. Every child of the gate must therefore be started through `procutil.Start`. `procutil.SetNonDumpable` clears the dumpable flag, so same-user processes cannot read the gate's memory or environment. Both are Linux only, as is `oom_score_adj`; elsewhere they do nothing. `Start` returns once the child's close-on-exec files are closed, which the kernel does before it makes the new program dumpable again, so for a moment the files under `/proc/<pid>` belong to root; opening `oom_score_adj` is therefore retried for up to 500 ms while it fails with `EACCES` or `EPERM`. A write refused once the file is open (a score below the child's `oom_score_adj_min`) is not retried. A failure that remains is logged.

Errors kept in the status and logged go through `Supervisor.ErrorText`, which replaces the server's URL (Go's HTTP errors quote it whole) with `<servers.NAME.http.url>` (`Supervisor.HideURL`) before redacting, and cuts at a character boundary (`redact.Cut`). For a legacy SSE server it first replaces the last 8 URLs `legacyTransport` was asked to request (`endpointLog`, refused ones too, but not one over 8 KiB, which is never sent), as they are, as net/http writes them with the password as `***`, as Go quotes them and as JSON escapes them, since Go sends a query as the server wrote it, with characters no URL scanner would take for part of a URL. Then it replaces every URL on the server's host, on any port and in any letter case or with trailing dots, query and all (`hideHost`), since the message endpoint carries the session id, which lets anyone who holds it post to the session; it runs first because the SDK's endpoint is the stream's URL with `?sessionid=` added, and replacing the URL alone would leave the query behind. A URL runs from its scheme over the characters of RFC 3986 (and the backslash of escapes); one on another host ends where the next scheme begins, so that a URL glued onto it is found. Only the authority is read before the host is compared, and it ends before the next URL's slashes, so the scan reads each byte once however many URLs are glued together. Punctuation that ends a sentence after a URL stays. `FuzzSSEHideEndpoint` checks that the session id of any endpoint a server can name, after the endpoint's own query, is gone from the error that the gate's HTTP client returns for a POST to it.

Child stderr goes through a `LineLog`: up to 8 KiB of each line is read and redacted. A line longer than that is redacted twice, as read and without its last 256 bytes, and only the start on which both agree is kept, so a secret across the cut is not half kept even when redaction shrinks the text. The result is cut at 4 KiB, logged under a rate limit (20 lines a second, bursts of 100) and kept in a 64 KiB ring that outlives restarts, in which each line counts with its newline, so empty lines are evicted too. Each kept line wakes `Wait`, since the ring is part of `Status`.

## HTTP

The SDK's streamable client transport gets an `http.Client` whose transport wraps a clone of the default one. It adds the configured headers, follows no redirects, and limits responses:

- an error response body is cut at 64 KiB;
- a JSON body is read into memory up to `maxMessageBytes`; a larger one (or a larger `Content-Length`) is replaced by a JSON-RPC error for the request id found in the POST body, which is decoded only then, so the SDK fails only that call instead of the connection;
- an event stream passes through one event at a time; an event over the limit is dropped and, when it is the response to the call that opened the stream, replaced by an error event. The SDK's own `MaxEventSize` is set slightly higher, as a backstop.

Compressed responses are decoded by the Go transport before the limits apply; `Accept-Encoding` cannot be configured.

### Legacy HTTP+SSE

A server with `transport: sse` uses the SDK's `SSEClientTransport` with the same size-limited client, wrapped in `sseTransport`. The SDK ties the stream's GET to the context `Connect` is given, so `sseTransport.Connect` gives it a context of its own, which the connect's context cancels only until the stream is open and `Close` cancels after. Its connection records the requests in flight in a `pendingCalls` set, the one `lineConn` uses: every response arrives on the one stream, so the event limiter fails the request named by a dropped response when the set holds it, rather than the call that opened the stream. A POST that fails is returned marked as rejected by the transport (code -32005), as the streamable client does, so it fails its own request and not the session; a stream that ends closes the session. The transport carries no version with `server/discover`, so without a pin the supervisor offers `2025-11-25` with `initialize` and no sub-deadline, and nothing is learned or reported as pinned.

The server names the message endpoint in the stream's first event, and the SDK resolves it against `url`, so it can point anywhere. `legacyTransport`, the outermost round tripper, refuses a request whose origin (scheme, host and port, with the default port made explicit) differs from `url`'s, or whose URL has user information or is longer than 8 KiB, before the headers or a token are added; the initialize POST then fails and the connect with it. The SDK's SSE client has no `OAuthHandler`, so `legacyTransport` also does what the streamable client does with one: it adds the access token from `TokenSource`, sends without one when the refresh token was rejected (`invalid_grant`), and on a 401 or 403 hands the request as sent to `Authorize` and sends it once more when that succeeds.

### OAuth

A server with an `oauth` block gets an `oauth.Source` as the transport's `OAuthHandler` (see [OAuth](oauth.md)), or as `legacyTransport`'s authorizer on the legacy transport. Before each connect the supervisor asks it for a usable grant; without one, the connect fails with a `LoginRequiredError`, the state becomes `needs-login`, the error is logged once, and the loop keeps trying after the backoff without counting restarts or leaving `needs-login` while the grant is unusable. A call that fails while the grant is unusable kicks the watch loop into a probe once the call has ended, and a failed probe with the grant unusable closes the session at once.
