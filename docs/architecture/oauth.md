# OAuth

[Docs](../README.md) / [Architecture](README.md) / **OAuth**

How mcp-gate is the OAuth client of the HTTP servers with an `oauth` block. The behaviour is specified in [`openspec/specs/oauth/spec.md`](../../openspec/specs/oauth/spec.md); the commands are in [auth](../commands/auth.md).

## Libraries

The SDK provides the parts that are about MCP: `oauthex.GetProtectedResourceMetadata` and `oauthex.GetAuthServerMeta` (or `auth.GetAuthServerMetadata`, which tries the well-known locations of an issuer) read and check the metadata documents, `oauthex.ParseWWWAuthenticate` reads the 401 challenge, and the streamable client transport takes an `auth.OAuthHandler`. `golang.org/x/oauth2` builds the authorization URL with the PKCE challenge and generates the verifier, and its `TokenSource` is the type the transport asks for.

The SDK's own `auth.AuthorizationCodeHandler` is not used: it runs the whole flow inside the transport when a request gets 401, which a headless gate must never do, has no place to keep the registered client and the refresh token across processes, and cannot read metadata from a configured URL. Token requests (the code exchange and refreshes) are the package's own `requestToken`, because a refresh through `x/oauth2` cannot carry the `resource` parameter, and because its errors quote the response body. Registration is its own for the same reason.

## Login

`BeginLogin` sends the server an unauthenticated `ping` and parses the challenge of a 401 answer. It reads the protected resource metadata at the challenge's URL or at the well-known locations (`prmCandidates`; for an endpoint ending in a slash, such as `/mcp/`, also accepting metadata that names it without the slash), then the authorization server's metadata, at `authServerMetadataURL` when set; `issuerOf` derives the issuer that document must name from its well-known form. The metadata documents are fetched through the SDK with a client whose transport sets no `DialContext`, so that the SDK clones it with its dial guard against private and reserved addresses (which it drops when a proxy is configured); keep-alives are off, since that clone cannot be closed. The other requests (the challenge, token and registration requests) go through `NewHTTPClient(serverURL)`, whose transport (`guardedTransport` in [`dial.go`](../../internal/oauth/dial.go)) dials with a `net.Dialer` whose `Control` refuses non-public addresses (`nonPublic`: netip's classes plus carrier-grade NAT, NAT64, 6to4, Teredo and other reserved ranges). `Control` sees the address after resolution, so DNS rebinding is caught at the dial; redirects are not followed at all. Non-public addresses are allowed when the configured server URL is written with one or with a local name (`localHost`, decided once when the client is built); resolving the server's name is deliberately not enough, because whoever runs a remote server's DNS could make it look local. A server on a LAN under a DNS name is therefore treated as public. Connections to the configured server's own host:port (`guard.server`) are checked only against `alwaysRefused`, since the MCP connection goes there unguarded anyway; that lets a server on a LAN or tailnet name answer the challenge, though the SDK's metadata guard still refuses its private metadata. `alwaysRefused` (link-local, the cloud metadata addresses, and IPv6 forms embedding IPv4: IPv4-compatible, IPv4-translated, NAT64, 6to4, Teredo; never loopback) is refused in every case. With a proxy from the environment, the dial goes to the proxy, which is allowed by its host and port; `proxyFor` refuses a cloud metadata name (`metadataName`) whatever the server, and a target written as a refused address, a numeric form such as `127.1` or `0x7f000001` (`numericHost`), or, for a server that is not local, a local, single-label or private-suffix name (`internalName`: `.internal`, `.local`, `.lan`, `.home.arpa` and the like), and other names are resolved by the proxy, unchecked: names that resolve to private addresses (wildcard DNS services, internal names) are not caught behind a proxy. The client is the configured one, the previous grant's registered one when it is for the same issuer and redirect URL, or a new registration. The authorization URL carries a `rand.Text` state, the S256 challenge and the resource.

`Pending.Complete` parses the pasted address, checks the redirect URL, the error, the state (in constant time) and the issuer (RFC 9207), and exchanges the code. `auth login` saves the grant under the store's lock.

## Logout

`auth logout` loads and deletes the grant file under the store's lock and lets the lock go before any network request, so that a refresh waiting for the lock (at most 40 seconds) is not held up by the authorization server. It then calls `Revoke` ([`revoke.go`](../../internal/oauth/revoke.go)) with the grant in memory, which reads the authorization server's metadata again, from `authServerMetadataURL` (whose issuer must be the grant's) or from the grant's issuer, through the same metadata client as a login. The grant does not record the revocation endpoint, so grants saved by any version can be revoked and the file format is unchanged. When the metadata names a `revocation_endpoint` that `config.SecureURL` accepts, `Revoke` posts the refresh token and then the access token there with `NewHTTPClient(serverURL)`, the client authenticated by `clientRequest` exactly as for the token endpoint. Status 200 counts as revoked, and so does `unsupported_token_type` for the access token once the refresh token is revoked (RFC 7009 makes access-token revocation optional); an error names the status and error code, never the description or a token.

## Store

A `Store` is `<state dir>/oauth`. `Save` writes a temporary file (0600) in that directory, syncs, renames and syncs the directory; the directory is created, or reset, to 0700. `load` opens with `O_NOFOLLOW`, checks the mode on the open file, reads at most 1 MiB and decodes strictly. `Lock` takes `flock` on `<server>.lock`. Each load remembers a stamp of the file (identity, size, modification time), which tells a `Source` when another process has written it.

## Source

A `Source` is the transport's `OAuthHandler` and its own `oauth2.TokenSource`. Every `Token` call compares the file's stamp with the one it read, so that a new login or a logout is noticed at the next request, and refreshes the access token when it expires within a minute, or half its lifetime for a short-lived one. `Authorize`, which the transport calls on 401 and 403, refreshes on a 401 to the current token and returns nil, so the transport retries once; a 401 whose challenge names `insufficient_scope` (`insufficientScope`) is treated like a 403, failing the request without a refresh or a count. The third 401 in a row to a token that the previous such refresh obtained, or a refresh refused with `invalid_grant`, `invalid_client` or `unauthorized_client`, marks the grant dead until the file changes. The count starts again when the server accepts such a token: the supervisor's HTTP client (`limitTransport` in `internal/downstream`) calls `Authorizer.Accepted` with every request answered 2xx, and `Source.Accepted` clears the count when the request carried the token the last 401 refresh obtained. That state sits under its own leaf mutex, so a response never waits for a refresh in progress; `Authorize` lets that mutex go during its refresh, so an `Accepted` for the token that just got the 401 can reset the count meanwhile, leaving it one lower, which only errs towards keeping the grant. A refresh runs under the store's lock (polled with `LOCK_NB` for at most 40 seconds); when the file changed while it waited, the file is read anew and wins, and the refresh goes on only when the grant it finds still needs one, so that a logout, a new login or another process's refresh is never overwritten. Refreshes run on the `Source`'s mutex, so one server refreshes once at a time; a refresh started by a 401 runs on a context that the request's end does not cancel, so that a rotated refresh token is not lost. `Source.Close` closes a channel that `refreshLocked` watches, ending a wait for the lock (`Store.Lock` takes a context) but not a token request already sent, which could otherwise lose a rotated refresh token; `Supervisor.Stop` calls it through `Authorizer.Close`, because the SDK holds its connection mutex while it waits for a token, which would otherwise keep a stop waiting past its limit when another process holds the lock.

Errors carry the token endpoint's status and error code (anything but lower-case letters and underscores becomes `unknown`); the description, which a server could fill with anything, is kept only for `auth login`. Transport errors are stripped of their URL.
